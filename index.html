HTMT 🗣️ 📄

HyperText Markup Transcript is a human-readable, machine-readable markup language for representing conversations as structured, temporal, semantically meaningful documents.

Core definition: HTMT is a serialization format for conversations. It represents not only what was said, but who said it, when it occurred, what it meant, how it relates to surrounding discourse, and what actions, decisions, references, or events emerged from it.

Status of this document

This is the final specification of HTMT 1.0, published by TechJoy. It supersedes the earlier conceptual draft; Appendix D lists every substantive change. The format, schema, and examples defined here are stable: documents that conform to this specification will remain conforming under all future 1.x revisions (see Section 17).

Errata and proposals are accepted through the specification's public repository. Normative content consists of the body sections and Appendices A–C; Appendices D and E and all examples are informative except where an example is explicitly labelled normative.

Conventions

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in BCP 14 [RFC 2119] [RFC 8174] when, and only when, they appear in all capitals.

Element names are written <turn>; attribute names are written speaker. Element and attribute names in this specification belong to the HTMT namespace (Section 4.2) unless stated otherwise. The terms defined in Section 3 are used with their defined meaning throughout.

Three kinds of conformance target are addressed: a document (an HTMT file or byte stream), a processor (software that reads HTMT), and a producer (software that writes HTMT). Requirements are stated against the target they bind.

1. Purpose and Scope

HTML describes documents. HTMT describes conversations over time.

HTMT is an interchange format for meeting transcripts, support sessions, interviews, podcasts, recorded calls, AI conversations, hearings, collaborative work sessions, video transcripts, and other forms of dialogic or event-driven communication. It preserves the structure and semantics of a conversation in a form that remains readable without specialized software.

Human-readable

A valid HTMT file is understandable in a text editor without a parser. Markup is additive: stripping every tag leaves the words that were said.

Machine-readable

HTMT is well-formed XML with a published schema. Existing XML tooling parses, validates, queries, and transforms it with no HTMT-specific code.

Temporal

Turns and events carry optional media-relative and absolute timestamps, so a transcript can drive playback, alignment, and chronology.

Semantic

Inline annotations record the role or consequence of an utterance — question, answer, decision, action, claim, risk — without replacing its literal wording.

1.1 In scope

  • The document syntax, element vocabulary, attribute semantics, and data types of HTMT 1.0.
  • Rules for identity, cross-reference, and timeline ordering within and between transcripts.
  • The extension mechanism and the compatibility guarantees processors can rely on.
  • Conformance requirements for documents, processors, and producers, and a normative schema.

1.2 Out of scope (non-goals)

  • Rendering. HTMT defines meaning, not appearance. No styling vocabulary is provided and none is planned for the core.
  • Transport and storage. HTMT is a file format. Streaming, synchronization, and live-update protocols are left to applications.
  • Speech recognition and diarization. HTMT records the output of those processes; it does not constrain how they are performed.
  • Authentication and integrity. HTMT carries claims about speakers, models, and confidence. Verifying them (signatures, provenance chains) is layered on by applications, not built into the format (see Section 14).
  • A universal transcription schema. Domain vocabularies (medical, legal, sales, support) belong in extensions (Section 12), never in the core.

2. Design Principles

  1. Conversation-first. Speaker turns are the primary unit of discourse. Everything else annotates, groups, or times them.
  2. Semantics over presentation. HTMT describes meaning and structure; rendering is implementation-defined.
  3. Progressive complexity. A minimal transcript is a root, a body, and turns. Timestamps, participants, semantics, media, and metadata are optional layers.
  4. Graceful degradation. A processor that understands nothing beyond turns still shows the complete conversation. Unknown elements never hide text.
  5. Extensibility without fragmentation. Domain semantics are added through XML namespaces, so the core stays small and extensions cannot collide.
  6. Stable identity. Turns and semantic objects may carry identifiers that are durable, unique, and addressable by URI fragment from inside or outside the document.
  7. Transport independence. HTMT is a document format, not a protocol.
  8. AI-native without being AI-dependent. Humans, software agents, and model-generated discourse are represented with the same primitives; none is privileged.
  9. Boring technology. HTMT is strictly XML 1.0 so that validators, XPath, XSLT, editors, and security hardening already exist for it.

3. Document Model

An HTMT document is a conversation: an ordered timeline of turns and events, optionally grouped into topics, optionally attributed to declared participants, optionally aligned to media, and optionally annotated with semantic objects that give utterances operational meaning.

HTML Document → Elements → Meaning → Presentation
HTMT Conversation → Turns → Meaning → Timeline

3.1 Terms

TermDefinition
turnOne contribution to the conversation by one speaker, represented by a <turn> element. A turn is the primary unit of discourse.
utterance textThe concatenation, in document order, of all character data descendant from a <turn>, after whitespace normalization (Section 4.6). Semantic and extension elements inside a turn contribute their text to the utterance; they annotate it, they do not replace it.
eventA non-speech occurrence on the timeline (silence, laughter, a participant joining, a screen share, a tool call), represented by <event>.

participantA person or agent declared in <participants> and referenced by the speaker and owner attributes.
semantic objectAn instance of a semantic element (Section 8): question, answer, decision, action, claim, fact, risk, note, quote.
identifierThe value of an id attribute. Identifiers are unique within a document and addressable as URI fragments.

transcript

├── participants?    person* | agent*
├── media*           audio/video/text sources the timeline aligns to

4. Document Syntax

4.1 XML profile

An HTMT document MUST be a well-formed XML 1.0 document [XML] that conforms to Namespaces in XML [XML-NAMES]. It MUST be encoded as UTF-8. The XML declaration is OPTIONAL; when present it MUST NOT declare any encoding other than UTF-8. A byte order mark MAY be present and MUST be ignored.

Element and attribute names are case-sensitive. All names defined by this specification are lowercase ASCII; multi-word names use a hyphen (screen-share).

4.2 Namespace and version

The HTMT 1.0 namespace is the IRI https://thetechjoy.com/htmt/1.0. The root element and every core element MUST be in this namespace; producers SHOULD declare it as the default namespace on the root. Core attributes are unprefixed and in no namespace.

The root element MUST carry a version attribute whose value is 1.0. The namespace identifies the vocabulary; the version identifies the revision of this specification the document claims conformance with. Future 1.x revisions keep the same namespace and increment version; a processor MUST accept any 1.x value it does not recognize and process the document under the 1.0 rules (Section 17).

4.3 Minimum valid document

<transcript xmlns="https://thetechjoy.com/htmt/1.0" version="1.0">
  <body>
    <turn speaker="Logan">Did the deployment finish?</turn>
    <turn speaker="Priya">Yes.</turn>
  </body>
</transcript>

4.4 Recommended document structure

<?xml version="1.0" encoding="UTF-8"?>
<transcript
  xmlns="https://thetechjoy.com/htmt/1.0"
  version="1.0"
  id="standup-2026-08-27"
  title="Engineering Standup"
  date="2026-08-27T09:00:00-05:00"
  duration="00:18:42"
  xml:lang="en">

  <meta>…</meta>
  <participants>…</participants>
  <media … />
  <body>…</body>

</transcript>

4.5 Prohibited XML features

An HTMT document MUST NOT contain a document type declaration (<!DOCTYPE>), internal or external entity declarations, or references to external entities. Only the five predefined entities (&amp; &lt; &gt; &quot; &apos;) and numeric character references MAY be used. A processor MUST reject a document containing a DOCTYPE and MUST configure its XML parser to disable DTD loading, external entity resolution, and network access (Section 14.1). Processing instructions other than the XML declaration are permitted and MUST be ignored by processors that do not recognize them. Comments are permitted and carry no meaning.

4.6 Whitespace

Whitespace in utterance text is insignificant by default, so that authors may indent markup freely. When computing utterance text, a processor MUST collapse each run of whitespace characters (U+0020, U+0009, U+000A, U+000D) to a single U+0020 and strip leading and trailing whitespace from the turn as a whole, exactly as HTML does for normal flow text. An element whose nearest xml:space ancestor-or-self has the value preserve is exempt: its character data MUST be preserved verbatim. Whitespace that appears only between child elements of <transcript>, <meta>, <participants>, <body>, and <topic> is ignorable.

4.7 Language

The language of utterance text is indicated with the standard xml:lang attribute [BCP 47], which MAY appear on any element and inherits in the usual way. Producers SHOULD set it on the root. A turn in a different language from the transcript SHOULD carry its own xml:lang.

Normative intent: a processor MUST preserve and present the text contained in elements it does not understand, whether they are core elements it chooses not to interpret or extension elements. Unknown markup never causes readable transcript content to disappear.

5.5 <body>

The timeline container. Content: any sequence of <topic>, <turn>, <event>, <note>, and extension elements. Exactly one <body> MUST be present; it MAY be empty. There are no attributes beyond the common ones.

Topics group the timeline; they never reorder it. Topic boundaries are a sectioning hint from which processors can derive chapters, navigation, and summaries. A topic MAY be empty and MAY contain other topics to any depth.

    We should verify the export before billing runs.
  </action>

AttributeTypeMeaning

Content is inline content: character data interleaved with <ref>, semantic elements, and extension elements in any order and nesting. The text of nested elements belongs to the utterance (3.1). A turn with no text and no children is permitted and represents a contribution with no transcribed content (for example, an inaudible turn, which SHOULD additionally carry an <event type="inaudible"> sibling or a <note>).

5.8 <event>

Defined in Section 10. Events share the turn's temporal attributes and inline content model, add a required type, and MAY carry speaker to attribute the event to a participant.

5.9 <ref>

Defined in Section 9. A <ref> wraps inline content and links it to a resource via href.

7. Temporal Model

Timestamps are optional at every level. The same syntax therefore represents a live meeting, a typed chat, a podcast, or an asynchronous AI conversation. When present, timestamps refine the timeline; they never override it.

7.1 Ordering rules

  • Timeline order (3.1) is document order. A processor MUST present turns and events in document order regardless of their timestamps.
  • Producers SHOULD emit turns in non-decreasing start order. Overlapping speech is represented by overlapping start/end ranges on consecutive turns, not by reordering or splitting the source.
  • Processors MUST NOT assume turns are non-overlapping, contiguous, or gap-free.
  • start MAY appear without end. end MUST NOT appear without start, and MUST NOT be earlier than start.
  • Timestamps on a <topic> SHOULD enclose the timestamps of its timed descendants.

7.2 Media time

start, end, and duration are clock-times measured from the time base: transcript time 00:00:00. For a recorded conversation, the time base is normally the start of the primary recording. A timed turn:

<turn id="t42" speaker="logan" start="00:13:42.220" end="00:13:49.810">
  We should verify the export before billing runs.
</turn>

7.3 Absolute time

Wall-clock time is expressed with the separate datetime attribute, never by placing a date-time in start. When transcript/@date is a datetime, a processor MAY derive the absolute time of any timed turn as date + start; an explicit datetime on a turn takes precedence over the derived value. Asynchronous conversations (chat, e-mail-like threads, AI sessions) typically carry datetime and no media time at all.

7.4 Media synchronization

To seek a media resource to a turn, a processor computes media-time = start + media/@offset. When several <media> elements are declared, a turn or event selects one with its media attribute; otherwise the first declared media applies. A processor MAY use temporal attributes to seek media when a user selects a turn or semantic object, and to highlight the current turn during playback.

8. Semantic Elements

Semantic elements let transcript text carry operational or interpretive meaning. They are annotations on discourse: a semantic element wraps the words that express it, so the words remain part of the utterance and remain visible to a processor that ignores the annotation.

All semantic elements take inline content and MAY carry an id and a summary. summary is a short normalized restatement of the object for indexes, task lists, and decision logs ("Deploy Monday"); it is metadata, never part of the utterance text, and it is where paraphrase belongs. They MAY nest (a <quote> inside a <claim>, a <ref> inside an <action>). Except for <note>, they MUST appear inside a <turn> or <event>; <note> MAY additionally appear directly in <body> or <topic>, where it represents an editorial annotation that nobody said.

ElementMeaningAttributes
<question>A question posed by the speaker.id — give one whenever an answer is expected.
<answer>A response to a specific question.to required: idref of the <question> answered.
<decision>A decision expressed in the conversation.status: proposed | accepted | rejected | superseded (default proposed); supersedes: idref of an earlier decision this one replaces.
<action>An action item, assigned or inferred.owner: participant id or label; due: date; status: open | done | cancelled (default open).
<claim>A factual or inferential assertion whose truth is not established within the conversation.confidence: the speaker's or annotator's confidence in the claim; source: URI of supporting material.
<fact>A statement treated as established within the conversation's context.source: URI.
<risk>A risk, concern, or possible adverse condition.severity: low | medium | high | critical.
<note>An editorial or system annotation.author: participant id or label; type: token, e.g. summary, correction, redaction, context.
<quote>Material the speaker is quoting rather than asserting.source: URI, which MAY be a fragment reference to the turn being quoted (#t12).

8.1 Question and answer

<turn speaker="sam" start="00:08:31">
  <question id="q17">Who is going to validate the export?</question>
</turn>

<turn speaker="logan" start="00:08:45">
  <answer to="q17">
    <action id="a3" owner="logan" due="2026-08-27" status="open" summary="Validate export">
      I'll validate it this afternoon.
    </action>
  </answer>
</turn>

A question MAY receive any number of answers, including none. An <answer> MUST reference a question in the same document; cross-document answers are expressed with <ref>.

8.2 Decision lifecycle

<turn speaker="logan">
  <decision id="d4" status="proposed" summary="Deploy Friday">
    I think we should deploy this Friday.
  </decision>
</turn>

<turn speaker="priya">
  Friday collides with the billing run.
  <decision id="d5" status="accepted" supersedes="d4" summary="Deploy Monday">
    Monday instead.
  </decision>
</turn>

Status reflects the state as of the end of the document: when d5 supersedes d4, a producer that rewrites the document SHOULD set d4 to superseded; a processor MUST treat a decision that is the target of a supersedes as superseded even if its own status was not updated.

8.3 Claims, facts, and confidence

The distinction between <claim> and <fact> is epistemic status within the conversation, not objective truth. A confidence on a claim is the speaker's or annotator's; a confidence on a turn is transcription accuracy. Processors MUST NOT conflate the two.

Annotation, not replacement: a processor that removes every semantic element but keeps its content MUST obtain the same utterance text. Producers MUST NOT place inside a semantic element words that were not part of the utterance; a normalized restatement goes in the summary attribute, and longer editorial commentary in a <note>.

9. HyperText References

The "HyperText" in HTMT is a design commitment: a transcript can link to resources, identifiers, other transcripts, and exact locations inside transcripts, using ordinary URIs.

<ref href="https://example.com/spec">Inventory Specification</ref>

<ref href="https://tracker.example.com/browse/OPS-2309" type="ticket">OPS-2309</ref>

<ref href="billing-2026-08-20.htmt#t184">Earlier billing discussion</ref>

<ref href="#d4">the Friday deployment decision</ref>
AttributeTypeMeaning
href requiredURIThe target. Relative references resolve against the document base URI.
typetokenOptional hint about the kind of target (ticket, document, transcript, dashboard, person). Not registered; processors MUST tolerate unknown values.

9.1 Fragment identifiers

The fragment identifier of a URI that resolves to an HTMT document MUST be interpreted as the value of an id attribute in that document. #t184 therefore addresses the turn, topic, event, media, or semantic object whose id is t184. This is the only fragment syntax defined for application/htmt+xml; processors MUST treat an unresolvable fragment as a reference to the whole document.

A fragment-only href (#d4) is an internal reference and MUST resolve within the document (13.1). A reference to another transcript is an ordinary relative or absolute URI with an optional fragment; no dedicated attributes are needed and none are defined.

9.2 URI schemes

Any scheme MAY appear in href, src, and source, including application-specific schemes. Producers SHOULD prefer https URLs to proprietary schemes so that references stay resolvable outside the producing application. Processors MUST treat all references as untrusted (Section 14).

10. Events

HTMT models more than spoken language. Events preserve contextual occurrences on the timeline: silence, laughter, participants joining and leaving, screen sharing, shared files, recording boundaries, and — in agent conversations — tool invocations.

<event type="silence" start="00:02:14" duration="00:00:03.200" />

<event type="laughter" start="00:03:02" />

<event type="join" datetime="2026-08-27T09:02:10-05:00" speaker="sam" />

<event type="screen-share" start="00:08:11" end="00:09:40" speaker="priya">
  Inventory Dashboard
</event>

<event type="file-shared" start="00:10:02" speaker="logan">
  <ref href="./inventory-report.xlsx">Inventory Report</ref>
</event>
AttributeTypeMeaning
type requiredtokenKind of event. Well-known values are listed in Appendix C; any other token MAY be used and MUST be tolerated.
ididAddressable identifier.
speakerparticipant id or labelParticipant the event is attributed to (who joined, who shared, which agent called a tool).

Event content is inline content describing the event. It is not utterance text: an event's text is never attributed to a speaker as something they said. An event MAY be empty.

11. Agents and AI Conversations

HTMT treats software agents as first-class participants rather than forcing them into a human speaker model. An agent is declared with <agent>, speaks through ordinary <turn> elements, and acts through <event> elements.

<transcript xmlns="https://thetechjoy.com/htmt/1.0" version="1.0"
            xmlns:tool="https://example.com/ns/tool-calls">
  <participants>
    <person id="user" name="Logan" />
    <agent id="assistant" name="Assistant" model="example-model-2" provider="Example AI" />
  </participants>

  <body>
    <turn id="t1" speaker="user" datetime="2026-10-28T14:02:11-05:00">
      Explain why our inventory numbers drift.
    </turn>

    <event type="tool-call" speaker="assistant" datetime="2026-10-28T14:02:12-05:00">
      <tool:call name="query_inventory" args='{"window":"7d"}' />
    </event>

    <event type="tool-result" speaker="assistant" datetime="2026-10-28T14:02:14-05:00">
      <tool:result name="query_inventory" status="ok" />
    </event>

    <turn id="t2" speaker="assistant" datetime="2026-10-28T14:02:15-05:00">
      There are several possible causes.
      <claim confidence="0.82">
        Timing differences between systems are the most likely contributor to the observed drift.
      </claim>
    </turn>
  </body>
</transcript>
  • Model, provider, tool, runtime, and generation metadata MAY be represented; none of it is required for portability. A processor MUST render an agent conversation correctly with every <agent> attribute except id absent.
  • Tool invocations and results are events of type tool-call and tool-result. Their payloads are application-specific and SHOULD be carried in an extension namespace, as above, so the core does not have to standardize tool schemas.
  • Hidden reasoning, system prompts, and other content not shown to a human participant SHOULD NOT be emitted as turns. If retained, it SHOULD be an extension element or an <event>, so that a basic processor presenting "what was said" does not misattribute it.
  • Statements by an agent about its own identity, model, or confidence are claims, not verified facts (14.3).

12. Extensibility

The HTMT core is deliberately small and this specification does not grow it for domain needs. Domain vocabularies are introduced as elements and attributes in a namespace other than the HTMT namespace, using standard XML namespace declarations.

<transcript xmlns="https://thetechjoy.com/htmt/1.0" version="1.0"
            xmlns:sup="https://support.example.com/ns/htmt">
  <meta>
    <sup:ticket id="T-48213" priority="p2" />
  </meta>
  <body>
    <turn speaker="customer" sup:sentiment="negative">
      The <sup:product sku="A1-200">A1 scanner</sup:product> stopped syncing yesterday.
    </turn>
  </body>
</transcript>

12.1 Where extensions may appear

  • Extension attributes MAY appear on any HTMT element.
  • Extension elements MAY appear as children of <meta>, <participants>, <person>, <agent>, <media>, <body>, <topic>, and anywhere inline content is allowed (inside turns, events, refs, and semantic elements).
  • Extension elements MAY contain HTMT <ref> and semantic elements, so that text inside an extension keeps its hypertext and semantic affordances.
  • Extension elements MUST NOT appear as direct children of <transcript>; put document-level extension data in <meta>.

12.2 Requirements on extensions

  • Extension names MUST be in a namespace whose IRI is controlled by the extension's author. The x- prefix convention of the conceptual draft is withdrawn; unprefixed element names in the HTMT namespace are reserved for this specification and its revisions.
  • An extension MUST NOT redefine the meaning of a core element or attribute, and MUST NOT require a processor to understand it in order to recover the utterance text.
  • Text inside an extension element that is inline within a turn is utterance text. An extension that needs to carry non-spoken text inside a turn MUST put it in attributes, not character data.
  • Extension authors SHOULD publish a schema and SHOULD document which extension elements may be stripped without loss of the conversation.

12.3 Processing unknown content

A processor MUST accept any extension element or attribute, in any permitted position, without error. It MUST preserve the character data of unknown inline elements as utterance text, MAY ignore the element itself, and SHOULD preserve unknown markup on round-trip when it rewrites a document.

13. Conformance

13.1 Conforming documents

A document conforms to HTMT 1.0 if and only if all of the following hold:

  1. It is a well-formed XML 1.0 document encoded as UTF-8, with no DOCTYPE and no entity declarations (4.1, 4.5).
  2. Its root is <transcript> in the HTMT namespace with version="1.0", and it is valid against the schema in Appendix A.
  3. Every id value is unique within the document.
  4. Every to, supersedes, and media attribute, and every fragment-only href or source, resolves to an element in the document.
  5. If <participants> is present, every speaker, owner, and author value equals a declared participant id.
  6. Every end is accompanied by a start no later than it; every duration that accompanies start and end equals their difference.
  7. Every <answer>'s to targets a <question>, and every supersedes targets a <decision>.

Items 1–2 are mechanically checkable with any XML parser and RELAX NG validator; items 3–7 are the integrity rules and require a small amount of application logic. The reference validator published with this specification checks all seven.

13.2 Conforming processors

Two processor classes are defined. A product MUST state which class it claims.

13.3 Conforming producers

A producer MUST emit only conforming documents. It SHOULD declare participants, assign ids to turns, set xml:lang, and emit transcript/@date as a datetime with offset. It MUST NOT emit a confidence it did not measure or estimate, and MUST NOT place non-spoken words inside a turn's character data. A producer that edits an existing document SHOULD preserve identifiers and unknown markup.

Compatibility rule: semantic richness is strictly additive. A document that uses every feature of this specification remains fully useful to a Basic processor.

14. Security and Privacy Considerations

Transcripts routinely contain sensitive personal, organizational, legal, or operational information, and they are frequently produced by automated systems whose output is unverified. The format does not make its content trustworthy; processors and producers must.

14.1 XML parsing

HTMT inherits XML's attack surface and closes it by profile. Processors MUST disable DTD processing, internal and external entity expansion, external parameter entities, XInclude, and network access in their XML parser, and MUST reject documents containing a DOCTYPE. This eliminates XXE, entity-expansion denial of service ("billion laughs"), and SSRF through entity resolution. Processors SHOULD enforce size and nesting limits appropriate to their environment.

14.2 References and media

  • All href, src, and source values are untrusted input. Processors MUST NOT automatically fetch, execute, or open them without user intent, and SHOULD restrict automatic resolution to an allow-list of schemes (normally https and same-origin relative references).
  • Application-specific URI schemes MUST NOT be dispatched to the operating system by default.
  • Processors that render transcripts as HTML MUST escape all character data and attribute values, including those from extension elements, and MUST NOT emit href values of javascript:, data:, or other executable schemes as live links.

14.3 Trust in metadata

Speaker identity, agent model and provider, authorship, timestamps, confidence values, and every semantic annotation are claims made by the producer. A processor MUST NOT present them as verified unless it has verified them by means outside this specification (for example a detached signature over the document, or provenance metadata in an extension namespace). In particular, an <agent> attribution does not establish that a given model produced a turn, and a human <person> attribution does not establish that the person said it.

14.4 Privacy and redaction

  • Producers SHOULD minimize personal data: participant hrefs, meta properties, and extension payloads should not carry identifiers or attributes the use case does not need.
  • The format is designed so that redaction tools can remove, independently of one another: utterance text, participant identities (replace name and href, keep id), temporal information, references, media associations, semantic annotations, and extension content. A redacted span SHOULD be marked with <note type="redaction"> so that the gap is visible rather than silent.
  • Because identifiers may be embedded in URIs that leave the document (…#t184), producers SHOULD NOT derive id values from personal data.
  • Transcripts of AI conversations may embed user-supplied text that attempts to instruct downstream processors. A processor that feeds HTMT content to a language model SHOULD treat utterance text as data, not instructions, and SHOULD preserve speaker boundaries when doing so.

16. Relationship to Other Formats

FormatPrimary question answeredHTMT distinction
Plain textWhat text exists?HTMT adds participant, temporal, semantic, and relational structure while remaining readable as text.
SRTWhat caption appeared, and when?HTMT represents discourse and meaning, not subtitle timing; it has no notion of a caption frame.
WebVTTWhat timed text cues belong to this media?HTMT adds identities, semantic objects, topics, actions, and hypertext relationships. A WebVTT file is losslessly expressible as HTMT turns; the reverse is not true.
HTMLHow is a document structured and presented?HTMT's native model is a conversation timeline, not a page. HTMT is XML, not HTML; it has no presentation vocabulary.
TEI (spoken-text module)How is a speech corpus encoded for scholarship?TEI is far larger and optimized for linguistic analysis. HTMT is a small operational interchange format; a TEI transcription can be projected onto HTMT with loss of linguistic detail.
Vendor JSON exportsHow does one application serialize its transcript?HTMT is a portable interchange syntax with shared semantic primitives and no application-specific schema.
Conceptual distinction:
SRT / WebVTT: "What was said, and when?"
HTMT: "Who said what, when, in response to what, what did it mean, what was decided, and what does it connect to?"

17. Versioning and Governance

  • The namespace IRI https://thetechjoy.com/htmt/1.0 is permanent for all 1.x revisions. A revision that changes the namespace is, by definition, HTMT 2.0.
  • Minor revisions (1.1, 1.2, …) MAY add elements, attributes, enumeration values, and well-known event types, and MAY relax constraints. They MUST NOT remove or rename anything, tighten a constraint so that a 1.0-conforming document becomes non-conforming, or change the meaning of existing markup. Consequently every 1.0 document is a valid 1.x document, and a 1.0 processor can process any 1.x document under the graceful-degradation rules.
  • Errata correct the text of this document without changing requirements; they are published as a dated revision of this page.
  • Changes are proposed and discussed in the public repository. Proposals that would enlarge the core with domain vocabulary will be redirected to extensions; the thesis of this specification is that the core stays small.
  • The schema in Appendix A, the reference validator, and the examples are published alongside this document and versioned with it.
Specification thesis: HTMT is not a universal transcription schema. Its value is a small, durable conversation model that remains readable by people, useful to conventional software, and structurally rich enough for AI-era communication.

Appendix A. RELAX NG Schema (normative)

The schema is given in RELAX NG compact syntax [RNC] and is distributed as htmt-1.0.rnc. It is the normative definition of content models and attribute lexical types. It does not express the integrity rules of 13.1 (items 3–7); the reference validator (tools/validate.py) checks both. An equivalent schema in RELAX NG XML syntax is distributed as htmt-1.0.rng for tools that do not read the compact syntax; where the two differ, htmt-1.0.rnc governs.

fraction     = 1*6DIGIT

LALPHA       = %x61-7A                 ; a-z

idref        = NCName

confidence   = "0" [ "." 1*DIGIT ] / "1" [ "." 1*"0" ] / "." 1*DIGIT

datetime     = date-time               ; [RFC 3339] section 5.6, offset SHOULD be present
date         = full-date / date-time   ; [RFC 3339] section 5.6

uri          = IRI-reference           ; [RFC 3987]
