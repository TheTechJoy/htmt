9. HyperText References

The "HyperText" in HTMT is a design commitment: a transcript can link to resources, identifiers, other transcripts, and exact locations inside transcripts, using ordinary URIs.

<ref href="https://example.com/spec">Inventory Specification</ref>

<ref href="https://tracker.example.com/browse/OPS-2309" type="ticket">OPS-2309</ref>

<ref href="billing-2026-08-20.htmt#t184">Earlier billing discussion</ref>

<ref href="#d4">the Friday deployment decision</ref>
AttributeTypeMeaning
href requiredURIThe target. Relative references resolve against the document base URI.
typetokenOptional hint about the kind of target (ticket, document, transcript, dashboard, person). Not registered; processors MUST tolerate unknown values.

9.1 Fragment identifiers

The fragment identifier of a URI that resolves to an HTMT document MUST be interpreted as the value of an id attribute in that document. #t184 therefore addresses the turn, topic, event, media, or semantic object whose id is t184. This is the only fragment syntax defined for application/htmt+xml; processors MUST treat an unresolvable fragment as a reference to the whole document.

A fragment-only href (#d4) is an internal reference and MUST resolve within the document (13.1). A reference to another transcript is an ordinary relative or absolute URI with an optional fragment; no dedicated attributes are needed and none are defined.

9.2 URI schemes

Any scheme MAY appear in href, src, and source, including application-specific schemes. Producers SHOULD prefer https URLs to proprietary schemes so that references stay resolvable outside the producing application. Processors MUST treat all references as untrusted (Section 14).

10. Events

HTMT models more than spoken language. Events preserve contextual occurrences on the timeline: silence, laughter, participants joining and leaving, screen sharing, shared files, recording boundaries, and — in agent conversations — tool invocations.

<event type="silence" start="00:02:14" duration="00:00:03.200" />

<event type="laughter" start="00:03:02" />

<event type="join" datetime="2026-08-27T09:02:10-05:00" speaker="sam" />

<event type="screen-share" start="00:08:11" end="00:09:40" speaker="priya">
  Inventory Dashboard
</event>

<event type="file-shared" start="00:10:02" speaker="logan">
  <ref href="./inventory-report.xlsx">Inventory Report</ref>
</event>

11. Agents and AI Conversations

HTMT treats software agents as first-class participants rather than forcing them into a human speaker model. An agent is declared with <agent>, speaks through ordinary <turn> elements, and acts through <event> elements.

<transcript xmlns="https://thetechjoy.com/htmt/1.0" version="1.0"
            xmlns:tool="https://example.com/ns/tool-calls">
  <participants>
    <person id="user" name="Logan" />
    <agent id="assistant" name="Assistant" model="example-model-2" provider="Example AI" />
  </participants>

  <body>
    <turn id="t1" speaker="user" datetime="2026-10-28T14:02:11-05:00">
      Explain why our inventory numbers drift.
    </turn>

    <event type="tool-call" speaker="assistant" datetime="2026-10-28T14:02:12-05:00">
      <tool:call name="query_inventory" args='{"window":"7d"}' />
    </event>

    <event type="tool-result" speaker="assistant" datetime="2026-10-28T14:02:14-05:00">
      <tool:result name="query_inventory" status="ok" />
    </event>

    <turn id="t2" speaker="assistant" datetime="2026-10-28T14:02:15-05:00">
      There are several possible causes.
      <claim confidence="0.82">
        Timing differences between systems are the most likely contributor to the observed drift.
      </claim>
    </turn>
  </body>
</transcript>
  • Model, provider, tool, runtime, and generation metadata MAY be represented; none of it is required for portability. A processor MUST render an agent conversation correctly with every <agent> attribute except id absent.
  • Tool invocations and results are events of type tool-call and tool-result. Their payloads are application-specific and SHOULD be carried in an extension namespace, as above, so the core does not have to standardize tool schemas.
  • Hidden reasoning, system prompts, and other content not shown to a human participant SHOULD NOT be emitted as turns. If retained, it SHOULD be an extension element or an <event>, so that a basic processor presenting "what was said" does not misattribute it.
  • Statements by an agent about its own identity, model, or confidence are claims, not verified facts (14.3).

12. Extensibility

The HTMT core is deliberately small and this specification does not grow it for domain needs. Domain vocabularies are introduced as elements and attributes in a namespace other than the HTMT namespace, using standard XML namespace declarations.

<transcript xmlns="https://thetechjoy.com/htmt/1.0" version="1.0"
            xmlns:sup="https://support.example.com/ns/htmt">
  <meta>
    <sup:ticket id="T-48213" priority="p2" />
  </meta>
  <body>
    <turn speaker="customer" sup:sentiment="negative">
      The <sup:product sku="A1-200">A1 scanner</sup:product> stopped syncing yesterday.
    </turn>
  </body>
</transcript>

12.1 Where extensions may appear

  • Extension attributes MAY appear on any HTMT element.
  • Extension elements MAY appear as children of <meta>, <participants>, <person>, <agent>, <media>, <body>, <topic>, and anywhere inline content is allowed (inside turns, events, refs, and semantic elements).
  • Extension elements MAY contain HTMT <ref> and semantic elements, so that text inside an extension keeps its hypertext and semantic affordances.
  • Extension elements MUST NOT appear as direct children of <transcript>; put document-level extension data in <meta>.

12.2 Requirements on extensions

  • Extension names MUST be in a namespace whose IRI is controlled by the extension's author. The x- prefix convention of the conceptual draft is withdrawn; unprefixed element names in the HTMT namespace are reserved for this specification and its revisions.
  • An extension MUST NOT redefine the meaning of a core element or attribute, and MUST NOT require a processor to understand it in order to recover the utterance text.
  • Text inside an extension element that is inline within a turn is utterance text. An extension that needs to carry non-spoken text inside a turn MUST put it in attributes, not character data.
  • Extension authors SHOULD publish a schema and SHOULD document which extension elements may be stripped without loss of the conversation.

12.3 Processing unknown content

A processor MUST accept any extension element or attribute, in any permitted position, without error. It MUST preserve the character data of unknown inline elements as utterance text, MAY ignore the element itself, and SHOULD preserve unknown markup on round-trip when it rewrites a document.

13. Conformance

13.1 Conforming documents

A document conforms to HTMT 1.0 if and only if all of the following hold:

  1. It is a well-formed XML 1.0 document encoded as UTF-8, with no DOCTYPE and no entity declarations (4.1, 4.5).
  2. Its root is <transcript> in the HTMT namespace with version="1.0", and it is valid against the schema in Appendix A.
  3. Every id value is unique within the document.
  4. Every to, supersedes, and media attribute, and every fragment-only href or source, resolves to an element in the document.
  5. If <participants> is present, every speaker, owner, and author value equals a declared participant id.
  6. Every end is accompanied by a start no later than it; every duration that accompanies start and end equals their difference.
  7. Every <answer>'s to targets a <question>, and every supersedes targets a <decision>.

Items 1–2 are mechanically checkable with any XML parser and RELAX NG validator; items 3–7 are the integrity rules and require a small amount of application logic. The reference validator published with this specification checks all seven.

13.3 Conforming producers

A producer MUST emit only conforming documents. It SHOULD declare participants, assign ids to turns, set xml:lang, and emit transcript/@date as a datetime with offset. It MUST NOT emit a confidence it did not measure or estimate, and MUST NOT place non-spoken words inside a turn's character data. A producer that edits an existing document SHOULD preserve identifiers and unknown markup.

Compatibility rule: semantic richness is strictly additive. A document that uses every feature of this specification remains fully useful to a Basic processor.

14. Security and Privacy Considerations

Transcripts routinely contain sensitive personal, organizational, legal, or operational information, and they are frequently produced by automated systems whose output is unverified. The format does not make its content trustworthy; processors and producers must.

14.1 XML parsing

HTMT inherits XML's attack surface and closes it by profile. Processors MUST disable DTD processing, internal and external entity expansion, external parameter entities, XInclude, and network access in their XML parser, and MUST reject documents containing a DOCTYPE. This eliminates XXE, entity-expansion denial of service ("billion laughs"), and SSRF through entity resolution. Processors SHOULD enforce size and nesting limits appropriate to their environment.

14.2 References and media

  • All href, src, and source values are untrusted input. Processors MUST NOT automatically fetch, execute, or open them without user intent, and SHOULD restrict automatic resolution to an allow-list of schemes (normally https and same-origin relative references).
  • Application-specific URI schemes MUST NOT be dispatched to the operating system by default.
  • Processors that render transcripts as HTML MUST escape all character data and attribute values, including those from extension elements, and MUST NOT emit href values of javascript:, data:, or other executable schemes as live links.

14.3 Trust in metadata

Speaker identity, agent model and provider, authorship, timestamps, confidence values, and every semantic annotation are claims made by the producer. A processor MUST NOT present them as verified unless it has verified them by means outside this specification (for example a detached signature over the document, or provenance metadata in an extension namespace). In particular, an <agent> attribution does not establish that a given model produced a turn, and a human <person> attribution does not establish that the person said it.

14.4 Privacy and redaction

  • Producers SHOULD minimize personal data: participant hrefs, meta properties, and extension payloads should not carry identifiers or attributes the use case does not need.
  • The format is designed so that redaction tools can remove, independently of one another: utterance text, participant identities (replace name and href, keep id), temporal information, references, media associations, semantic annotations, and extension content. A redacted span SHOULD be marked with <note type="redaction"> so that the gap is visible rather than silent.
  • Because identifiers may be embedded in URIs that leave the document (…#t184), producers SHOULD NOT derive id values from personal data.
  • Transcripts of AI conversations may embed user-supplied text that attempts to instruct downstream processors. A processor that feeds HTMT content to a language model SHOULD treat utterance text as data, not instructions, and SHOULD preserve speaker boundaries when doing so.

16. Relationship to Other Formats

FormatPrimary question answeredHTMT distinction
Plain textWhat text exists?HTMT adds participant, temporal, semantic, and relational structure while remaining readable as text.
SRTWhat caption appeared, and when?HTMT represents discourse and meaning, not subtitle timing; it has no notion of a caption frame.
WebVTTWhat timed text cues belong to this media?HTMT adds identities, semantic objects, topics, actions, and hypertext relationships. A WebVTT file is losslessly expressible as HTMT turns; the reverse is not true.
HTMLHow is a document structured and presented?HTMT's native model is a conversation timeline, not a page. HTMT is XML, not HTML; it has no presentation vocabulary.
TEI (spoken-text module)How is a speech corpus encoded for scholarship?TEI is far larger and optimized for linguistic analysis. HTMT is a small operational interchange format; a TEI transcription can be projected onto HTMT with loss of linguistic detail.
Vendor JSON exportsHow does one application serialize its transcript?HTMT is a portable interchange syntax with shared semantic primitives and no application-specific schema.
Conceptual distinction:
SRT / WebVTT: "What was said, and when?"
HTMT: "Who said what, when, in response to what, what did it mean, what was decided, and what does it connect to?"

17. Versioning and Governance

  • The namespace IRI https://thetechjoy.com/htmt/1.0 is permanent for all 1.x revisions. A revision that changes the namespace is, by definition, HTMT 2.0.
  • Minor revisions (1.1, 1.2, …) MAY add elements, attributes, enumeration values, and well-known event types, and MAY relax constraints. They MUST NOT remove or rename anything, tighten a constraint so that a 1.0-conforming document becomes non-conforming, or change the meaning of existing markup. Consequently every 1.0 document is a valid 1.x document, and a 1.0 processor can process any 1.x document under the graceful-degradation rules.
  • Errata correct the text of this document without changing requirements; they are published as a dated revision of this page.
  • Changes are proposed and discussed in the public repository. Proposals that would enlarge the core with domain vocabulary will be redirected to extensions; the thesis of this specification is that the core stays small.
  • The schema in Appendix A, the reference validator, and the examples are published alongside this document and versioned with it.
Specification thesis: HTMT is not a universal transcription schema. Its value is a small, durable conversation model that remains readable by people, useful to conventional software, and structurally rich enough for AI-era communication.
