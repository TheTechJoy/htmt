5. Core Elements

This section defines every element in the HTMT namespace. The schema in Appendix A is the normative statement of content models and attribute types; where prose and schema disagree, the schema governs content and the prose governs meaning. Attributes shared by all elements — xml:lang, xml:space, and namespaced extension attributes — are not repeated in each table.

<agent>Declares an AI or software participant.Optional
<media>Associates an audio, video, or text source with the timeline.Optional, repeatable

5.1 <transcript>

The root element. Content, in order: meta?, participants?, media*, body.

AttributeTypeMeaning
version requiredliteral 1.0Specification revision claimed (4.2).
ididStable identifier for the conversation. SHOULD be unique within the producing system so cross-transcript references stay unambiguous.
titletextHuman-readable title.
datedate | datetimeWhen the conversation took place. A datetime with offset is RECOMMENDED; it anchors media time to wall-clock time (7.3).
durationclock-timeTotal length of the timeline.

5.2 <meta> and <property>

<meta> contains zero or more <property name="…">value</property> elements and any extension elements. name is a token (Section 6). Property names are not registered; producers SHOULD prefer short, lowercase, hyphenated names and SHOULD use extension elements rather than properties when a value has internal structure. The same name MAY appear more than once to express a multi-valued property. Processors MUST NOT require any property to be present.

<meta>
  <property name="source-system">Example Meetings</property>
  <property name="transcription-method">asr</property>
  <property name="tag">engineering</property>
  <property name="tag">weekly</property>
</meta>

5.3 <participants>, <person>, <agent>

<participants>
  <person id="logan" name="Logan Schmidt" role="lead" />
  <person id="priya" name="Priya Nair" />
  <agent id="assistant" name="Assistant" model="example-model-2" provider="Example AI" />
</participants>
AttributeApplies toMeaning
id requiredperson, agentIdentifier referenced by speaker and owner.
nameperson, agentDisplay name. If absent, processors SHOULD display the id.
roleperson, agentFree-text role in this conversation (host, interviewer, customer, moderator, tool).

Speaker resolution. When a document contains a <participants> element, every speaker and owner value in the document MUST equal the id of a declared participant. When no <participants> element is present, speaker and owner values are literal display labels; two turns with the same label SHOULD be treated as the same speaker. Producers SHOULD declare participants whenever more is known about a speaker than a label. A <turn> without a speaker attribute is unattributed.

5.4 <media>

<media id="recording" type="audio" src="./engineering-standup.mp3" duration="00:18:42" />

5.5 <body>

The timeline container. Content: any sequence of <topic>, <turn>, <event>, <note>, and extension elements. Exactly one <body> MUST be present; it MAY be empty. There are no attributes beyond the common ones.

5.6 <topic>

<topic id="inventory" name="Inventory" start="00:00:00" end="00:02:10">
  <turn speaker="sam">Let's talk about inventory drift.</turn>
  …
  <topic name="Reconciliation job">…</topic>
</topic>
AttributeTypeMeaning
name requiredtextHuman-readable subject of the section.
ididAddressable identifier.
start, endclock-timeExtent on the timeline. If absent, the extent is that of the first and last timed descendants.

Topics group the timeline; they never reorder it. Topic boundaries are a sectioning hint from which processors can derive chapters, navigation, and summaries. A topic MAY be empty and MAY contain other topics to any depth.

5.7 <turn>

<turn id="t42" speaker="logan" start="00:13:42.220" end="00:13:49.810" confidence="0.94">
  <action id="a7" owner="logan" due="2026-08-27" status="open" summary="Validate the billing export">
    We should verify the export before billing runs.
  </action>
</turn>
AttributeTypeMeaning
ididStable identifier. RECOMMENDED for every turn a producer may want to reference later.
speakerparticipant id or labelWho spoke (5.3).
start, endclock-timeMedia time of the first and last spoken word (Section 7).
datetimedatetimeAbsolute wall-clock time at which the turn began.
mediamedia idWhich declared <media> the temporal attributes refer to; default is the first declared media.
confidencedecimal 0–1Producer's confidence that the utterance text is an accurate transcription of what was said (typically ASR confidence). Unrelated to the truth of the content.

Content is inline content: character data interleaved with <ref>, semantic elements, and extension elements in any order and nesting. The text of nested elements belongs to the utterance (3.1). A turn with no text and no children is permitted and represents a contribution with no transcribed content (for example, an inaudible turn, which SHOULD additionally carry an <event type="inaudible"> sibling or a <note>).

5.8 <event>

Defined in Section 10. Events share the turn's temporal attributes and inline content model, add a required type, and MAY carry speaker to attribute the event to a participant.

5.9 <ref>

Defined in Section 9. A <ref> wraps inline content and links it to a resource via href.

7. Temporal Model

Timestamps are optional at every level. The same syntax therefore represents a live meeting, a typed chat, a podcast, or an asynchronous AI conversation. When present, timestamps refine the timeline; they never override it.

7.1 Ordering rules

  • Timeline order (3.1) is document order. A processor MUST present turns and events in document order regardless of their timestamps.
  • Producers SHOULD emit turns in non-decreasing start order. Overlapping speech is represented by overlapping start/end ranges on consecutive turns, not by reordering or splitting the source.
  • Processors MUST NOT assume turns are non-overlapping, contiguous, or gap-free.
  • start MAY appear without end. end MUST NOT appear without start, and MUST NOT be earlier than start.
  • Timestamps on a <topic> SHOULD enclose the timestamps of its timed descendants.

7.2 Media time

start, end, and duration are clock-times measured from the time base: transcript time 00:00:00. For a recorded conversation, the time base is normally the start of the primary recording. A timed turn:

<turn id="t42" speaker="logan" start="00:13:42.220" end="00:13:49.810">
  We should verify the export before billing runs.
</turn>

7.3 Absolute time

Wall-clock time is expressed with the separate datetime attribute, never by placing a date-time in start. When transcript/@date is a datetime, a processor MAY derive the absolute time of any timed turn as date + start; an explicit datetime on a turn takes precedence over the derived value. Asynchronous conversations (chat, e-mail-like threads, AI sessions) typically carry datetime and no media time at all.

7.4 Media synchronization

To seek a media resource to a turn, a processor computes media-time = start + media/@offset. When several <media> elements are declared, a turn or event selects one with its media attribute; otherwise the first declared media applies. A processor MAY use temporal attributes to seek media when a user selects a turn or semantic object, and to highlight the current turn during playback.

8. Semantic Elements

Semantic elements let transcript text carry operational or interpretive meaning. They are annotations on discourse: a semantic element wraps the words that express it, so the words remain part of the utterance and remain visible to a processor that ignores the annotation.

All semantic elements take inline content and MAY carry an id and a summary. summary is a short normalized restatement of the object for indexes, task lists, and decision logs ("Deploy Monday"); it is metadata, never part of the utterance text, and it is where paraphrase belongs. They MAY nest (a <quote> inside a <claim>, a <ref> inside an <action>). Except for <note>, they MUST appear inside a <turn> or <event>; <note> MAY additionally appear directly in <body> or <topic>, where it represents an editorial annotation that nobody said.

ElementMeaningAttributes
<question>A question posed by the speaker.id — give one whenever an answer is expected.
<answer>A response to a specific question.to required: idref of the <question> answered.
<decision>A decision expressed in the conversation.status: proposed | accepted | rejected | superseded (default proposed); supersedes: idref of an earlier decision this one replaces.
<action>An action item, assigned or inferred.owner: participant id or label; due: date; status: open | done | cancelled (default open).
<claim>A factual or inferential assertion whose truth is not established within the conversation.confidence: the speaker's or annotator's confidence in the claim; source: URI of supporting material.
<fact>A statement treated as established within the conversation's context.source: URI.
<risk>A risk, concern, or possible adverse condition.severity: low | medium | high | critical.
<note>An editorial or system annotation.author: participant id or label; type: token, e.g. summary, correction, redaction, context.
<quote>Material the speaker is quoting rather than asserting.source: URI, which MAY be a fragment reference to the turn being quoted (#t12).

8.1 Question and answer

<turn speaker="sam" start="00:08:31">
  <question id="q17">Who is going to validate the export?</question>
</turn>

<turn speaker="logan" start="00:08:45">
  <answer to="q17">
    <action id="a3" owner="logan" due="2026-08-27" status="open" summary="Validate export">
      I'll validate it this afternoon.
    </action>
  </answer>
</turn>

A question MAY receive any number of answers, including none. An <answer> MUST reference a question in the same document; cross-document answers are expressed with <ref>.

8.2 Decision lifecycle

<turn speaker="logan">
  <decision id="d4" status="proposed" summary="Deploy Friday">
    I think we should deploy this Friday.
  </decision>
</turn>

<turn speaker="priya">
  Friday collides with the billing run.
  <decision id="d5" status="accepted" supersedes="d4" summary="Deploy Monday">
    Monday instead.
  </decision>
</turn>

Status reflects the state as of the end of the document: when d5 supersedes d4, a producer that rewrites the document SHOULD set d4 to superseded; a processor MUST treat a decision that is the target of a supersedes as superseded even if its own status was not updated.

8.3 Claims, facts, and confidence

The distinction between <claim> and <fact> is epistemic status within the conversation, not objective truth. A confidence on a claim is the speaker's or annotator's; a confidence on a turn is transcription accuracy. Processors MUST NOT conflate the two.

Annotation, not replacement: a processor that removes every semantic element but keeps its content MUST obtain the same utterance text. Producers MUST NOT place inside a semantic element words that were not part of the utterance; a normalized restatement goes in the summary attribute, and longer editorial commentary in a <note>.
