Status of this document

This is the final specification of HTMT 1.0, published by TechJoy. It supersedes the earlier conceptual draft; Appendix D lists every substantive change. The format, schema, and examples defined here are stable: documents that conform to this specification will remain conforming under all future 1.x revisions (see Section 17).

Errata and proposals are accepted through the specification's public repository. Normative content consists of the body sections and Appendices A–C; Appendices D and E and all examples are informative except where an example is explicitly labelled normative.

Conventions

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in BCP 14 [RFC 2119] [RFC 8174] when, and only when, they appear in all capitals.

Element names are written <turn>; attribute names are written speaker. Element and attribute names in this specification belong to the HTMT namespace (Section 4.2) unless stated otherwise. The terms defined in Section 3 are used with their defined meaning throughout.

Three kinds of conformance target are addressed: a document (an HTMT file or byte stream), a processor (software that reads HTMT), and a producer (software that writes HTMT). Requirements are stated against the target they bind.

1. Purpose and Scope

HTML describes documents. HTMT describes conversations over time.

HTMT is an interchange format for meeting transcripts, support sessions, interviews, podcasts, recorded calls, AI conversations, hearings, collaborative work sessions, video transcripts, and other forms of dialogic or event-driven communication. It preserves the structure and semantics of a conversation in a form that remains readable without specialized software.

Human-readable

A valid HTMT file is understandable in a text editor without a parser. Markup is additive: stripping every tag leaves the words that were said.

Machine-readable

HTMT is well-formed XML with a published schema. Existing XML tooling parses, validates, queries, and transforms it with no HTMT-specific code.

Temporal

Turns and events carry optional media-relative and absolute timestamps, so a transcript can drive playback, alignment, and chronology.

Semantic

Inline annotations record the role or consequence of an utterance — question, answer, decision, action, claim, risk — without replacing its literal wording.

1.1 In scope

  • The document syntax, element vocabulary, attribute semantics, and data types of HTMT 1.0.
  • Rules for identity, cross-reference, and timeline ordering within and between transcripts.
  • The extension mechanism and the compatibility guarantees processors can rely on.
  • Conformance requirements for documents, processors, and producers, and a normative schema.

1.2 Out of scope (non-goals)

  • Rendering. HTMT defines meaning, not appearance. No styling vocabulary is provided and none is planned for the core.
  • Transport and storage. HTMT is a file format. Streaming, synchronization, and live-update protocols are left to applications.
  • Speech recognition and diarization. HTMT records the output of those processes; it does not constrain how they are performed.
  • Authentication and integrity. HTMT carries claims about speakers, models, and confidence. Verifying them (signatures, provenance chains) is layered on by applications, not built into the format (see Section 14).
  • A universal transcription schema. Domain vocabularies (medical, legal, sales, support) belong in extensions (Section 12), never in the core.

2. Design Principles

  1. Conversation-first. Speaker turns are the primary unit of discourse. Everything else annotates, groups, or times them.
  2. Semantics over presentation. HTMT describes meaning and structure; rendering is implementation-defined.
  3. Progressive complexity. A minimal transcript is a root, a body, and turns. Timestamps, participants, semantics, media, and metadata are optional layers.
  4. Graceful degradation. A processor that understands nothing beyond turns still shows the complete conversation. Unknown elements never hide text.
  5. Extensibility without fragmentation. Domain semantics are added through XML namespaces, so the core stays small and extensions cannot collide.
  6. Stable identity. Turns and semantic objects may carry identifiers that are durable, unique, and addressable by URI fragment from inside or outside the document.
  7. Transport independence. HTMT is a document format, not a protocol.
  8. AI-native without being AI-dependent. Humans, software agents, and model-generated discourse are represented with the same primitives; none is privileged.
  9. Boring technology. HTMT is strictly XML 1.0 so that validators, XPath, XSLT, editors, and security hardening already exist for it.

3. Document Model

An HTMT document is a conversation: an ordered timeline of turns and events, optionally grouped into topics, optionally attributed to declared participants, optionally aligned to media, and optionally annotated with semantic objects that give utterances operational meaning.

HTMT Conversation → Turns → Meaning → Timeline

3.1 Terms

TermDefinition
turnOne contribution to the conversation by one speaker, represented by a <turn> element. A turn is the primary unit of discourse.
utterance textThe concatenation, in document order, of all character data descendant from a <turn>, after whitespace normalization (Section 4.6). Semantic and extension elements inside a turn contribute their text to the utterance; they annotate it, they do not replace it.
eventA non-speech occurrence on the timeline (silence, laughter, a participant joining, a screen share, a tool call), represented by <event>.
timeline orderDocument order of <turn> and <event> elements within <body>, descending into <topic> elements. Timeline order is authoritative; timestamps refine it but never reorder it.
participantA person or agent declared in <participants> and referenced by the speaker and owner attributes.
semantic objectAn instance of a semantic element (Section 8): question, answer, decision, action, claim, fact, risk, note, quote.
identifierThe value of an id attribute. Identifiers are unique within a document and addressable as URI fragments.
media timeA clock-time offset from the start of the transcript's time base (Section 7).

3.2 Structure

transcript
├── meta?            metadata not expressible as core attributes
├── participants?    person* | agent*
├── media*           audio/video/text sources the timeline aligns to
└── body             the timeline
    ├── topic*       (nestable) groups of the following, in order
    ├── turn*        speech; contains utterance text, refs, semantic objects
    ├── event*       non-speech occurrences
    └── note*        editorial annotations that are not utterances

4. Document Syntax

4.1 XML profile

An HTMT document MUST be a well-formed XML 1.0 document [XML] that conforms to Namespaces in XML [XML-NAMES]. It MUST be encoded as UTF-8. The XML declaration is OPTIONAL; when present it MUST NOT declare any encoding other than UTF-8. A byte order mark MAY be present and MUST be ignored.

Element and attribute names are case-sensitive. All names defined by this specification are lowercase ASCII; multi-word names use a hyphen (screen-share).

4.2 Namespace and version

The HTMT 1.0 namespace is the IRI https://thetechjoy.com/htmt/1.0. The root element and every core element MUST be in this namespace; producers SHOULD declare it as the default namespace on the root. Core attributes are unprefixed and in no namespace.

The root element MUST carry a version attribute whose value is 1.0. The namespace identifies the vocabulary; the version identifies the revision of this specification the document claims conformance with. Future 1.x revisions keep the same namespace and increment version; a processor MUST accept any 1.x value it does not recognize and process the document under the 1.0 rules (Section 17).

  <body>…</body>

4.5 Prohibited XML features

An HTMT document MUST NOT contain a document type declaration (<!DOCTYPE>), internal or external entity declarations, or references to external entities. Only the five predefined entities (&amp; &lt; &gt; &quot; &apos;) and numeric character references MAY be used. A processor MUST reject a document containing a DOCTYPE and MUST configure its XML parser to disable DTD loading, external entity resolution, and network access (Section 14.1). Processing instructions other than the XML declaration are permitted and MUST be ignored by processors that do not recognize them. Comments are permitted and carry no meaning.

4.6 Whitespace

Whitespace in utterance text is insignificant by default, so that authors may indent markup freely. When computing utterance text, a processor MUST collapse each run of whitespace characters (U+0020, U+0009, U+000A, U+000D) to a single U+0020 and strip leading and trailing whitespace from the turn as a whole, exactly as HTML does for normal flow text. An element whose nearest xml:space ancestor-or-self has the value preserve is exempt: its character data MUST be preserved verbatim. Whitespace that appears only between child elements of <transcript>, <meta>, <participants>, <body>, and <topic> is ignorable.

4.7 Language

The language of utterance text is indicated with the standard xml:lang attribute [BCP 47], which MAY appear on any element and inherits in the usual way. Producers SHOULD set it on the root. A turn in a different language from the transcript SHOULD carry its own xml:lang.

Normative intent: a processor MUST preserve and present the text contained in elements it does not understand, whether they are core elements it chooses not to interpret or extension elements. Unknown markup never causes readable transcript content to disappear.
